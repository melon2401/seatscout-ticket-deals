# SeatScout — project handoff and roadmap

Updated: 2026-11-12

This document transfers the product decisions, design direction, implementation state, and future plan from the original Codex development conversation. Read it before changing the project. Verify the code and deployed services rather than assuming this document is perfectly current.

## 1. Product vision

SeatScout is a no-login ticket comparison and market-intelligence website. A visitor searches for an artist, event, team, show, or venue; SeatScout compares official and third-party listings, makes fees and price types understandable, and helps the visitor decide where and when to buy.

The product should feel unusually polished and useful—not like a generic generated dashboard. Its personality is a vintage box office and old printed ticket, with contemporary interaction and data clarity.

Primary goals:

- Search official and resale ticket sources from one place.
- Tolerate misspellings and imperfect queries globally, not only for one artist.
- Compare final prices as fairly as provider data permits.
- Clearly distinguish live official prices, live resale prices, and estimates.
- Show price trends and collect new observations over time.
- Make venue zones interactive and connect them to relevant listings.
- Let visitors save deals locally without creating an account.
- Remain usable on free service tiers during the prototype stage.

## 2. Non-negotiable product decisions

- There is **no login or user account system** in the current product plan.
- Saved deals use browser `localStorage` and must survive refreshes on the same browser.
- Never display an estimate as live market data. Every price needs one of these labels:
  - `live_official`
  - `live_resale`
  - `estimated`
- Search correction must be general. For example, `Phobe Bridges` should sensibly resolve toward Phoebe Bridgers, but the implementation must also tolerate errors in other artists, events, teams, and venues.
- Selecting another event must update the entire market board. The Weeknd content must never remain visible after another event is selected.
- A price-history chart must represent stored observations. Until enough observations exist, show an honest sparse/empty state rather than inventing a historical trend.
- API keys, database credentials, and other secrets must never be committed, pasted into documentation, or rendered into browser JavaScript.
- Work should be delivered in focused, believable phases with small conventional commits. Do not fabricate or backdate git history.

## 3. Visual and interaction direction

The approved design language is already represented in `templates/index.html`, `static/app.css`, `static/app.js`, and `design/seatscout-vintage-target.png`.

Design characteristics:

- Warm cream paper, deep box-office red, mustard gold, olive green, and near-black ink.
- Editorial serif display type combined with compact monospaced labels.
- Printed texture, outlined panels, ticket stubs, perforated/ridged ticket edges, stamps, and restrained shadows.
- Large editorial headings and a vintage theatre/box-office identity.
- Ticket listings should look like old physical tickets without sacrificing readability.
- Avoid generic AI-sounding marketing copy. The earlier phrase “Every seller. One honest total.” was explicitly rejected and removed.
- Inspiration discussed during development included the layout/editorial energy of Goodcart's HEP reference and the comparison clarity of TicketWhiz. These are inspiration only; do not copy proprietary layouts or assets.

Interaction requirements:

- Hovering a venue zone highlights it and previews its starting price.
- Clicking a zone opens or navigates to an in-depth price/listing view filtered to that zone.
- Price-chart range controls (`7D`, `30D`, `90D`, `6M`) must change real chart data.
- Event/category filters, listing filters, sorting, save buttons, and calls to action must have real behavior.
- Ticket purchase buttons should lead to the provider's listing URL and clearly identify the provider.
- Responsive behavior must remain strong on mobile and desktop.

## 4. Current architecture

- Backend: Python with FastAPI.
- Rendering: Jinja template plus plain JavaScript and CSS.
- Production database: Neon Postgres.
- Local fallback database: SQLite.
- Python hosting: Render free web service.
- Scheduled collection: GitHub Actions hourly workflow.
- Static build: `dist/`, generated by `scripts/build_static.py`.
- No frontend framework is currently required.

Important locations:

- `app/main.py` — routes and API composition.
- `app/providers.py` — demo, Ticketmaster, and SeatGeek adapters.
- `app/storage.py` — SQLAlchemy snapshot persistence.
- `app/data.py` — demonstration events, offers, zones, and chart data.
- `templates/index.html` — server-rendered interface.
- `static/app.js` and `static/app.css` — browser behavior and styling.
- `scripts/refresh_prices.py` — scheduled snapshot collector.
- `.github/workflows/refresh-prices.yml` — hourly collection workflow.
- `render.yaml` — Render service configuration.

## 6. Providers and data truthfulness

Current provider intent:

- Ticketmaster Discovery API: event discovery, official links, and official price ranges when supplied.
- SeatGeek API: resale event data and market statistics when credentials are available.
- StubHub: planned only; legitimate partner access may be required.
- Ticket Evolution: planned commercial feed only.

Do not scrape sellers blindly. Before adding a provider, review its current API availability, terms, rate limits, attribution rules, and affiliate requirements. Prefer official APIs or approved partner feeds. A provider being named in the interface does not mean a working integration exists.

Provider results are currently normalized into common event dictionaries, but this is not yet a complete cross-market listing model. Ticketmaster's Discovery API often supplies event-level price ranges rather than exact seat inventory. Do not claim full fee-inclusive comparison unless the source actually supplies those amounts.

## 8. Known gaps and risks

- The page still mixes live search results with a market board originally built around hardcoded demo data.
- Venue zones and seller tickets are not yet derived from a shared live event/listing model.
- Chart controls and displayed trends need to read the history API for the active event.
- New events will initially have little or no meaningful historical data.
- Ticketmaster and SeatGeek event records need stronger cross-provider identity matching and deduplication.
- Search silently catches provider exceptions, making operational failures hard to diagnose.
- There is no caching, provider health telemetry, retry/backoff policy, or rate-limit protection.
- SeatGeek search currently ignores the selected city.
- `GET /api/events/{event_slug}` falls back to the first demo event for unknown slugs instead of returning `404`.
- “Watch price” is not a real alert service. With no accounts, alerts require a carefully chosen browser-local or optional email approach.
- StubHub and Ticket Evolution are placeholders, not live integrations.
- The API currently returns provider URLs but does not yet calculate a reliable all-in, fee-inclusive total across every source.
- Accessibility, keyboard navigation, reduced-motion behavior, loading states, empty states, and error messaging need a systematic pass.
- CORS must include the actual frontend origin(s). Keep the list narrow.

There are pre-existing uncommitted local changes in `app/storage.py` and `tests/test_app.py` that load `.env` earlier and isolate tests from production services. Review and test them before committing. There were also untracked `AGENTS.md` and `CLAUDE.md` files at handoff time; preserve and reconcile them deliberately.

## 9. Recommended roadmap

### Phase A — establish a trustworthy live baseline

1. Run the complete test suite and commit the pending test-isolation/database-loading work if it passes.
2. Verify `/api/health`, `/api/providers`, and live Ticketmaster search on Render.
3. Add structured logging for provider failures without logging credentials.
4. Add mocked tests for Ticketmaster success, empty results, invalid key, timeout, and rate limiting.
5. Confirm the hourly GitHub Actions job can write snapshots to Neon.
6. Display a visible source/type badge on every returned event and price.

Acceptance criteria: a real Ticketmaster query returns matching events; failures are visible to developers; demo fallback is visibly labelled; no secrets appear in responses or logs.

### Phase B — create a canonical event and listing model

1. Introduce normalized models for events, performances, venues, zones, listings, providers, price observations, and outbound URLs.
2. Preserve source-specific identifiers.
3. Match and deduplicate the same event across providers using artist/team, venue, local time, and city—not name alone.
4. Track currency and whether fees are included, excluded, unknown, or estimated.
5. Return a comparison response designed for the frontend rather than exposing provider-shaped dictionaries.

Acceptance criteria: multiple provider records for one performance appear on a single comparison page without merging unrelated events.

### Phase C — connect the whole interface to the selected event

1. Replace the hardcoded Weeknd market board with active-event state.
2. Update title, date, venue, zones, chart, seller strip, tickets, and outbound links together.
3. Add real loading, empty, partial-data, and provider-error states.
4. Ensure fuzzy search suggestions do not silently replace a query with the wrong event; show the correction to the visitor.
5. Return `404` for unknown event slugs.

Acceptance criteria: searching or selecting any result never leaves stale information from another event on screen.

### Phase D — real price history and market signals

1. Define a stable cross-provider event key.
2. Collect hourly snapshots for tracked events and viewed events within free-tier limits.
3. Wire `7D`, `30D`, `90D`, and `6M` controls to actual observations.
4. Show gaps honestly and disclose the number and age of observations.
5. Calculate low, median, official, and resale series only when supported by data.
6. Build a transparent market signal from documented factors such as current percentile, recent direction, inventory trend, and time until event.
7. Explain why the signal says “buy,” “wait,” or “insufficient data.”

Acceptance criteria: every plotted point can be traced to stored observations and no synthetic history is presented as recorded history.

### Phase E — zone-level exploration and listings

1. Create reusable venue-map metadata by venue and event configuration.
2. Connect hovered zones to live or estimated price summaries.
3. On click, filter or navigate to a detailed zone view with listings, price distribution, seller, row/section, quantity, accessibility, and fee status.
4. Provide an accessible non-map list with equivalent controls.
5. Avoid implying exact seat-map inventory when only broad price ranges exist.

Acceptance criteria: pointer and keyboard users can choose a zone and see only relevant, truthfully labelled listings.

### Phase F — saved deals and optional alerts without login

1. Harden the local saved-deal schema with stable IDs, migration/versioning, timestamps, and removal controls.
2. Allow comparisons among saved deals.
3. Let users set a local target price.
4. If email alerts are added, make them explicitly opt-in and store the minimum necessary information; do not introduce full accounts without a new product decision.

Acceptance criteria: saved deals remain accurate after refresh and visibly show when their price is stale.

### Phase G — additional sellers and fair totals

1. Add SeatGeek after validating current API access and production terms.
2. Pursue approved partner access for other marketplaces.
3. Normalize currencies and fee disclosure.
4. Rank by a clearly named comparable total; when fees are unknown, do not mix that price into an “all-in cheapest” claim.
5. Add affiliate disclosures where required.

Acceptance criteria: the “best deal” calculation compares like with like and explains exclusions.

### Phase H — production hardening

1. Add request caching, rate limiting, retries with bounded backoff, timeouts, and provider circuit breaking.
2. Add migrations rather than relying only on table creation at startup.
3. Add monitoring, privacy documentation, terms, affiliate disclosures, and an error-reporting strategy.
4. Run accessibility, security, performance, mobile, and cross-browser checks.
5. Add CI for tests, formatting/linting, and static-build verification.

## 10. Testing expectations

At minimum, preserve or add coverage for:

- Empty search and direct search.
- Misspelled artist, team, venue, and event queries.
- Correct city filtering.
- Provider success, empty response, malformed response, authentication failure, timeout, and rate limit.
- Demo fallback and truthful price labels.
- Snapshot persistence and history ranges.
- Unknown event `404`.
- Event switching with no stale market-board content.
- Local saved-deal add/remove/persistence behavior.
- Zone hover, click, and keyboard activation.
- No secrets embedded in `dist/` or API responses.
